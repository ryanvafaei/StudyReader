# StudyReader

Native macOS app for studying course material: read PDFs and Markdown, highlight and annotate them, review highlights with spaced repetition (FSRS-6), and export highlights to Google Docs so Gemini Notebook (formerly NotebookLM) can use them as a source. Single user, local-first, no backend server.

## Documents (read the relevant one before planning; don't load them for small fixes)

- `docs/SPEC.md`: features F-01…F-22 with acceptance criteria, build phases 0–3
- `docs/ARCHITECTURE.md`: layout, data model (SQL schema), anchoring, extraction, search, export, review, testing
- `docs/DEPENDENCIES.md`: allowed packages, reference repos and which files to read, Google setup
- `docs/decisions/`: ADRs 0001–0010; follow them, don't re-decide them

## Hard scope rules

- **No EPUB.** No EPUB parsing, rendering, Readium, types, stubs, or "future" hooks.
- macOS only. No iOS, iPadOS, web, or server targets.
- No features outside `docs/SPEC.md` unless the user asks. Propose additions; don't build them.
- No paid or cloud AI APIs. On-device Apple frameworks only (NaturalLanguage, FoundationModels, Vision).
- Never write annotations into the user's PDF files; the database is the source of truth.

## Stack

- Swift 6 (strict concurrency complete), SwiftUI + AppKit, deployment target **macOS 27.0**. No `#available` branches for earlier macOS.
- Project generated by **XcodeGen** from `project.yml`. Edit `project.yml`, never `.xcodeproj` (git-ignored).
- Packages (only these; ask before adding any other): GRDB 7.11+, swift-markdown 0.9+, swift-fsrs 5.0+ (FSRS-6), GoogleSignIn 10.1+.
- PDF: PDFKit. Markdown and PDF text view: swift-markdown → `NSAttributedString` in NSTextView (TextKit 2).
- Persistence: SQLite via GRDB (`DatabasePool`, WAL), FTS5 search.
- Export: GoogleSignIn (`drive.file` scope) + Drive API Markdown→Google Docs conversion via URLSession.
- Tests: Swift Testing (`import Testing`) for logic. UI flows at visual checkpoints get XCUITests in `StudyReaderUITests/` (ADR-0019).

## Commands

Always use these scripts, exactly as written (no pipes, redirects, `cd`, or chained commands). They run outside the Claude Code sandbox so Xcode can write its caches and download packages; nobody edits `scripts/` or `.claude/settings.json` except the user.

- Build: `./scripts/build.sh` (log: `build/build.log`)
- Test all: `./scripts/test.sh` (log: `build/test.log`)
- Test some: `./scripts/test.sh StudyReaderTests/<Suite>[/<test>] …`
- Fresh-clone check (committed files only): `./scripts/check-fresh-clone.sh`
- UI tests (take over the screen): `./scripts/uitest.sh [StudyReaderUITests/<Class>[/<test>] …]` (log: `build/uitest.log`, screenshots: `build/ui-screenshots/`)
- Run the app with an in-memory library for exploratory checks: `./scripts/run-app.sh` / `./scripts/run-app.sh stop` (log: `build/app.log`)
- LaunchServices check / cleanup of stale app copies: `./scripts/lsregister-clean.sh [--check]`
- Never call `xcodebuild` directly and never `rm -rf` the generated project; `xcodegen generate` (no cache) regenerates it.
- **Cloud sessions (Linux, no Xcode):** `build.sh`, `test.sh`, `uitest.sh` and `check-fresh-clone.sh` forward to `./scripts/ci.sh`, which runs the same step on GitHub Actions (macOS 27) and prints the result (ADR-0020). A run takes minutes (build ~10, unit tests ~15, UI tests ~30); give the Bash call a long timeout and wait for it. Logs and screenshots land in `build/ci/<run id>/`. `./scripts/ci.sh status` shows the latest `master` run. `run-app.sh` and `lsregister-clean.sh` need a Mac.

## Architecture rules (details in ARCHITECTURE.md)

- Feature folders under `StudyReader/Features/`, shared code in `StudyReader/Core/`.
- Views are thin; logic lives in `@MainActor @Observable` models and `Sendable` services/actors, which are unit-tested.
- Repositories are the only code that touches GRDB. `FileStore` is the only code that builds file paths.
- PDFKit isn't thread-safe: background work opens its own `PDFDocument`; never pass PDFKit objects across actors.
- Inject time (`Now`) and network (`HTTPClient`); never call `Date()` or `URLSession.shared` inside logic.
- Text anchors use UTF-16 offsets (NSRange). PDF anchors use page-space rects.

## Reference repos (`.references/`, read-only)

- Read only the files DEPENDENCIES.md §3 lists for your task. Never Glob, Grep, or Explore `.references/` broadly.
- Never open anything under `.references/reader-source/Reader/Formats/` except `Formats/PDF/` (the rest is EPUB/web code).
- Copying more than ~20 lines: keep the original copyright and license line in a comment and add an entry to `THIRD_PARTY_NOTICES.md`.

## Agent workflow (main session = orchestrator)

The main session coordinates and does not write feature code itself. Agents are in `.claude/agents/`.

| Agent | Model | Effort | Role |
|---|---|---|---|
| architect | Opus | high | Phase plan, task specs in `docs/tasks/phase-N/`, ADRs |
| data-layer, review-engine | Haiku | medium | Implement tasks assigned to them |
| ui-builder | Sonnet | medium | Implement UI and app-shell tasks (Sonnet since 2026-10-27) |
| pdf-engine, integrations | Sonnet | high | Implement tasks assigned to them |
| test-runner | Haiku | low | Build + full tests, failures only |
| code-reviewer | Sonnet | medium | Approve or request changes, per task |
| bug-hunter | Opus | high | End-of-phase bug hunt, report in `docs/bugs/` |
| ui-tester | Sonnet | high | Visual checkpoints: XCUITests + Peekaboo pass, report in `docs/checkpoints/` (ADR-0019) |

Effort comes from each agent's file. Override it per call only as the escalation rule says. Never set `CLAUDE_CODE_EFFORT_LEVEL` (it overrides every agent).

### Per phase
1. architect plans the phase. Show the user the task list and open questions before implementing.
2. For each task, in the order of `docs/tasks/phase-N/README.md`:
   1. Delegate to the task's agent with the spec path. Wait for its report. The implementer verifies with `./scripts/build.sh` and unit-test filters only; no UI test runs.
   2. As soon as the implementer reports, start code-reviewer (spec path and the implementer's report) and, in parallel, test-runner (CI build + full unit tests). Never run two CI jobs at once: overlapping `ci.sh` runs cancel each other, so only test-runner uses CI.
   3. Append one line to the spec's "Review log": `date, implementer <agent> <model> <effort> (reworks: effort), reviewer <agent> <model> <effort>: VERDICT, reason`. Approval counts only if CI passes.
   4. APPROVED and CI green: commit (one task per commit, message `TNN: <title>`), then `git push origin master`. Don't wait for the master CI run before the next task. If the report says "Visual check needed: yes", add its steps to VISUAL_CHECKS.md.
   5. CHANGES REQUESTED, or CI red: follow the escalation rule below, then repeat from step 2.
3. XCUITests run only at the checkpoints in VISUAL_CHECKS.md (T63, T69, T74), never per task. At each checkpoint:
   1. Run `./scripts/ci.sh status`. If a master run failed, stop and fix it first.
   2. Run ui-tester with the checkpoint name and its checklist (full UI suite, cloud mode on Linux).
   3. Only spec FAILs become fix tasks (through the same loop). Everything else (UX items, visual nits, open observations) goes into `docs/BACKLOG.md`. No polish tasks mid-phase. Ask the user only about NEEDS HUMAN items, then continue.
4. At the end of Phase 1, run one fix pass over `docs/BACKLOG.md` (tasks planned by architect).
5. When all tasks are approved, have test-runner run `./scripts/check-fresh-clone.sh`, then run bug-hunter. Turn its critical and high findings into fix tasks and run them through the same loop.

### Escalation rule
Count CHANGES REQUESTED verdicts per task (from its Review log).
- Haiku agent (data-layer, review-engine), 1st rejection: re-run the same agent with effort `high` for that call. Give it the spec and the review report.
- Haiku agent, 2nd rejection: re-run the same agent with model `sonnet` and effort `high` for that call. Give it the spec and both review reports.
- Sonnet agent (ui-builder, pdf-engine, integrations), 1st rejection: re-run the same agent with effort `high` for that call. Give it the spec and the review report. 2nd rejection: stop, summarize the problem, and ask the user how to proceed.
- Any review of a task that was escalated: run code-reviewer with effort `high` for that call.
- An implementer reporting BLOCKED: answer from the spec or ADRs if possible; otherwise ask the user. Don't guess.

### General rules
- Run one implementer at a time. Never run two agents that edit files in parallel.
- Keep diffs small; one task per commit, pushed to `master` right after (ADR-0020). Never force-push `master`, delete branches or rewrite history. Never base work on the `ci-scratch` branch (`ci.sh` rewrites it).
- UI and PDF-position changes can't be verified by reading code. Verify them with ui-tester (XCUITests + Peekaboo) at the checkpoints instead of claiming they work; until then list them in VISUAL_CHECKS.md. Ask the user only for what ui-tester marks NEEDS HUMAN.
- Only ui-tester controls the screen. Never run `uitest.sh`, `run-app.sh` or Peekaboo from another agent or in parallel with another agent.
- Don't read or print anything in `Secrets/`.

## Cloud sessions (ADR-0020)

A cloud session has `CLAUDE_CODE_REMOTE=true` and runs Linux without Xcode, the app or a screen.
- At the start, read `docs/HANDOFF.md`, then run `./scripts/ci.sh status`. Keep HANDOFF.md current at each checkpoint, phase change or open decision, and push it.
- Build and test through the scripts as usual; they run on CI (see Commands).
- Mac-only checks (ui-tester's Peekaboo pass, Finder drag-and-drop, light/dark appearance, keychain/Google sign-in, real-library behaviour) can't run here. List them under "Needs a Mac" in VISUAL_CHECKS.md with the task ID and exact steps, and keep going. The user checks them on the Mac.
- When something needs the user (a product decision, a BLOCKED report, a spec question), ask in the session, then continue with any task that doesn't depend on the answer. Don't guess.
- If CI itself fails (runner, signing, network) rather than the code, stop and report it with the run URL.

## Compact instructions

When compacting, keep: current phase and task, files changed, failing tests and their errors, open decisions. Drop exploration output and file dumps.
