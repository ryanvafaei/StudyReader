# StudyReader

Native macOS app for studying course material: read PDFs and Markdown, highlight and annotate them, review highlights with spaced repetition (FSRS-6), and export highlights to Google Docs so Gemini Notebook (formerly NotebookLM) can use them as a source. Single user, local-first, no backend server.

## Documents (read the relevant one before planning; don't load them for small fixes)

- `docs/SPEC.md`: features F-01…F-22 with acceptance criteria, build phases 0–3
- `docs/ARCHITECTURE.md`: layout, data model (SQL schema), anchoring, extraction, search, export, review, testing
- `docs/DEPENDENCIES.md`: allowed packages, reference repos and which files to read, Google setup
- `docs/decisions/`: ADRs 0001–0010; follow them, don't re-decide them

## Hard scope rules

- **No EPUB.** No EPUB parsing, rendering, Readium, types, stubs, or "future" hooks.
- macOS only. No iOS, iPadOS, web, or server targets.
- No features outside `docs/SPEC.md` unless the user asks. Propose additions; don't build them.
- No paid or cloud AI APIs. On-device Apple frameworks only (NaturalLanguage, FoundationModels, Vision).
- Never write annotations into the user's PDF files; the database is the source of truth.

## Stack

- Swift 6 (strict concurrency complete), SwiftUI + AppKit, deployment target **macOS 27.0**. No `#available` branches for earlier macOS.
- Project generated by **XcodeGen** from `project.yml`. Edit `project.yml`, never `.xcodeproj` (git-ignored).
- Packages (only these; ask before adding any other): GRDB 7.11+, swift-markdown 0.9+, swift-fsrs 5.0+ (FSRS-6), GoogleSignIn 10.1+.
- PDF: PDFKit. Markdown and PDF text view: swift-markdown → `NSAttributedString` in NSTextView (TextKit 2).
- Persistence: SQLite via GRDB (`DatabasePool`, WAL), FTS5 search.
- Export: GoogleSignIn (`drive.file` scope) + Drive API Markdown→Google Docs conversion via URLSession.
- Tests: Swift Testing (`import Testing`). XCUITest only when a flow can't be tested otherwise.

## Commands

- Generate project: `xcodegen generate --use-cache --quiet`
- Build: `xcodegen generate --use-cache --quiet && xcodebuild -project StudyReader.xcodeproj -scheme StudyReader -destination 'platform=macOS' build`
- Test: same with `test` instead of `build`
- Single test: add `-only-testing:StudyReaderTests/<Suite>/<test>`

## Architecture rules (details in ARCHITECTURE.md)

- Feature folders under `StudyReader/Features/`, shared code in `StudyReader/Core/`.
- Views are thin; logic lives in `@MainActor @Observable` models and `Sendable` services/actors, which are unit-tested.
- Repositories are the only code that touches GRDB. `FileStore` is the only code that builds file paths.
- PDFKit isn't thread-safe: background work opens its own `PDFDocument`; never pass PDFKit objects across actors.
- Inject time (`Now`) and network (`HTTPClient`); never call `Date()` or `URLSession.shared` inside logic.
- Text anchors use UTF-16 offsets (NSRange). PDF anchors use page-space rects.

## Reference repos (`.references/`, read-only)

## Agent workflow (main session = orchestrator)

The main session coordinates and does not write feature code itself. Agents are in `.claude/agents/`.

| Agent | Model | Role |
|---|---|---|
| architect | Opus | Phase plan, task specs in `docs/tasks/phase-N/`, ADRs |
| data-layer, ui-builder, review-engine | Haiku | Implement tasks assigned to them |
| pdf-engine, integrations | Sonnet | Implement tasks assigned to them |
| test-runner | Haiku | Build + full tests, failures only |
| code-reviewer | Sonnet | Approve or request changes, per task |
| bug-hunter | Opus | End-of-phase bug hunt, report in `docs/bugs/` |

### Per phase
1. architect plans the phase. Show the user the task list and open questions before implementing.
2. For each task, in the order of `docs/tasks/phase-N/README.md`:
   1. Delegate to the task's agent with the spec path. Wait for its report.
   2. Run test-runner. Wait for the result.
   3. Run code-reviewer with the spec path, the implementer's report, and the test result.
   4. Append one line to the spec's "Review log": date, model used, verdict, short reason.
   5. APPROVED: commit (one task per commit, message `TNN: <title>`). If the report says "Visual check needed: yes", ask the user to check before moving on.
   6. CHANGES REQUESTED: send the review issues back to the same agent and repeat from step 2.
3. When all tasks are approved, run bug-hunter. Turn its critical and high findings into fix tasks and run them through the same loop.

### Escalation rule
- A task on a Haiku agent that gets CHANGES REQUESTED twice: re-run it on the same agent with the model set to `sonnet` for that call. Give it the spec and both review reports.
- A task on Sonnet (pdf-engine, integrations, or an escalated task) that gets CHANGES REQUESTED twice: stop, summarize the problem, and ask the user how to proceed.
- An implementer reporting BLOCKED: answer from the spec or ADRs if possible; otherwise ask the user. Don't guess.

### General rules
- Run one implementer at a time. Never run two agents that edit files in parallel.
- Keep diffs small; one task per commit. Never push, force-push, or rewrite history unless the user asks.
- UI and PDF-position changes can't be verified by reading code. Ask the user for a screenshot instead of claiming it works.
- Don't read or print anything in `Secrets/`.

## Compact instructions

When compacting, keep: current phase and task, files changed, failing tests and their errors, open decisions. Drop exploration output and file dumps.
